# navigation-menu

2026-08-26, strategy: legacy-style classification (radix golden fetched from `https://ui.shadcn.com/r/styles/default/navigation-menu.json` for diff purposes only) + hand transform via the transformation engine (`universal-patterns.md`, `menus.md`, `class-mapping.md`). Verdict: essentially pristine vs golden (only Tailwind v4 syntax normalization — `top-[1px]`→`top-px`, `z-[1]`→`z-1`, bracket CSS vars → parens — plus formatting), migrated in place. This is the most structurally invasive file in the batch — see Behavior changes.

## Changed

- `packages/ui/src/components/navigation-menu.tsx`
  - `import * as NavigationMenuPrimitive from "@radix-ui/react-navigation-menu"` → `import { NavigationMenu as NavigationMenuPrimitive } from "@base-ui/react/navigation-menu"`.
  - `NavigationMenu` (Root) still auto-renders its viewport internally exactly like the original did with `<NavigationMenuViewport />` as a trailing child — the exported, consumer-facing composition API (`NavigationMenu > NavigationMenuList > NavigationMenuItem > NavigationMenuTrigger` + `NavigationMenuContent`) is UNCHANGED.
  - `NavigationMenuViewport` internally restructured from a manual `<div class="absolute ...">` wrapper around `NavigationMenuPrimitive.Viewport` into a full `Portal > Positioner > Popup > Viewport` composition, per `menus.md`: "Viewport moves out of Root into `Portal > Positioner > Popup > Viewport`". `Positioner` uses `side="bottom" align="center"` to approximate the old CSS-centered-below-list look (see Behavior changes #2 — this is a genuinely different positioning model, not a like-for-like translation).
  - CSS vars: `--radix-navigation-menu-viewport-height/width` → `--popup-height`/`--popup-width` on `Popup` (verified against `NavigationMenuContentDataAttributes`-adjacent d.ts and `menus.md`'s explicit nav-menu CSS var table, which names `Popup` specifically — not `--positioner-*`, which `universal-patterns.md`'s more general table lists as an alternative but is less specific for this component).
  - `NavigationMenuIndicator` retargeted from `.Indicator` to `.Icon` (see Behavior changes #1 — implemented as a real functional part, matching verified shadcn base-registry output, with the animation stripped since Base UI's `Icon` has no hook for it).
  - `NavigationMenuTrigger`'s chevron rotation: `group-data-[state=open]:rotate-180` → `group-data-popup-open:rotate-180` (Trigger's open marker, confirmed via `NavigationMenuTriggerDataAttributes.d.ts`).
  - `navigationMenuTriggerStyle` cva classes: `data-[state=open]:*` → `data-popup-open:*`.
  - `NavigationMenuContent`: dropped the `left-0 top-0 md:absolute md:w-auto` positioning classes — no longer meaningful since `Positioner` now owns all positioning (see Behavior changes #3). The `data-[motion=from-start|from-end|to-start|to-end]:*` slide classes were RESTATED (not translated 1:1) using `data-starting-style:`/`data-ending-style:` combined with `data-[activation-direction=left|right]:` — verified via `NavigationMenuContentDataAttributes.d.ts` that Base UI's `Content` has **no `data-motion` attribute at all**, only `data-open`/`data-closed`/`data-starting-style`/`data-ending-style`/`data-activation-direction` (`'left'|'right'|'up'|'down'`). This is a best-effort restatement per `class-mapping.md`'s explicit "restate the intent" guidance for animation idioms, not a verified pixel-identical port — see Behavior changes #4.
  - `NavigationMenuList`/`NavigationMenuTrigger`/`NavigationMenuContent`/`NavigationMenuIndicator` converted from `React.forwardRef<ElementRef, ComponentPropsWithoutRef>` to plain function components typed as `NavigationMenuPrimitive.<Part>.Props`. `NavigationMenuItem`/`NavigationMenuLink` remain bare re-exports (`const NavigationMenuItem = NavigationMenuPrimitive.Item;`), unchanged in shape from the original.
  - Leftover scan: `grep -n "radix-ui\|@radix-ui\|IconPlaceholder" packages/ui/src/components/navigation-menu.tsx` → clean.

## Behavior changes

- **`NavigationMenuIndicator` (now `Icon`) lost its enter/exit fade animation.** Verified via `NavigationMenuIconDataAttributes.d.ts` that Base UI's `Icon` part exposes ONLY `data-popup-open` — no `data-open`/`data-closed`/`data-starting-style`/`data-ending-style` hooks exist on it (unlike every other nav-menu part). The original's `data-[state=visible]:animate-in ... data-[state=hidden]:animate-out ...fade-in/fade-out` classes had no attribute to hang off of, so they were dropped; the indicator now appears/disappears instantly rather than fading. This matches the SKILL's hard rule ("NavigationMenu Indicator have no equivalent") in spirit — implemented as a real, styled part (matching verified shadcn base-registry `base-nova` output structurally) rather than an inert no-op, but the animated position-tracking behavior Radix had is genuinely gone.
- **Positioning model fundamentally changed.** Radix's `Viewport` was a single shared container, CSS-centered below the whole menu list (`absolute left-0 top-full ... justify-center`), not tied to any individual trigger. Base UI's `Positioner` is REAL per-trigger anchored positioning (the same mechanism `Menu`/`Popover`/`Tooltip` use), chosen here with `side="bottom" align="center"` to visually approximate the old look. This is not a class-level tweak — it is a different positioning engine — verify the popup lines up sensibly under each trigger, especially for triggers near the left/right edge of the viewport (Radix's shared-viewport approach never needed edge-collision handling; Base UI's positioner does it automatically but may behave differently near edges).
- **No `viewport={false}` inline-fallback mode.** Radix supported (unused in this project's current markup) a `viewport` boolean to render content inline instead of in the shared floating viewport, useful for a mobile/no-JS fallback. Base UI dropped this prop entirely (confirmed via `menus.md`: "`viewport` boolean prop removed"). There is no equivalent if a future consumer wants that fallback.
- **Enter/exit slide-direction animation is a best-effort restatement, not a verified port.** Radix's 4-state `data-motion` model (`from-start`/`from-end`/`to-start`/`to-end`) doesn't exist in Base UI at all; the replacement (`data-starting-style`/`data-ending-style` × `data-[activation-direction=left|right]`) was constructed by hand per the documented "restate the intent" pattern and should be visually checked when switching between adjacent nav items.
- **`NavigationMenuLink`'s close-on-select default flips.** Radix's `onSelect` closed the parent menu by default; Base UI's `Link` has `closeOnClick` defaulting to `false` (confirmed via `menus.md`'s Link table). A link inside a content panel will no longer auto-close the menu after being clicked unless a consumer explicitly passes `closeOnClick`. Left unpatched per the hard rule (flag, don't silently patch).

## Verify by hand

Since there are no live consumers today, this requires mounting a throwaway `<NavigationMenu>` with 2+ items each with `Trigger` + `Content`:

1. Click/hover a trigger; confirm the chevron rotates 180° (`data-popup-open`) and the content panel opens anchored below it.
2. Switch between two adjacent triggers; confirm the panel slides in a sensible direction (left/right) rather than popping instantly — this exercises the restated `data-activation-direction` animation.
3. Use content panels of very different sizes between two items; confirm the popup height/width (`--popup-height`/`--popup-width`) animates smoothly between them.
4. Click a `NavigationMenuLink` inside a content panel; confirm the menu closes as expected (or explicitly wire `closeOnClick` if it doesn't — Base UI's `Link.closeOnClick` defaults to `false`, unlike Radix which closed on select by default).
